## 内容引入

**3 分钟互动：一次问答，还是复杂任务？**

教师列出三类请求，请学生判断：

```text
1. 请解释一个概念，例如什么是氧化还原反应。
2. 请根据我提供的 3 道氧化还原反应错题找出共同错因，并说明如何避免。
3. 请根据我的错题记录和老师讲义，安排 5 天复习计划，生成自测题，
   收集我的答题结果，再调整后两天安排。
```

第一类通常一次回答就能完成；第二类需要分析已提供的材料，仍可能在一轮内完成。第三类需要持续推进：先理解目标，再调用课程 RAG 匹配讲义和错题资料，再统计错题，再计划，再出题，再根据反馈调整。

本节课核心：复杂任务需要规划、执行、思考模式、CoT/ToT/GoT 提示引导、工具调用、观察结果和反馈调整。

## 知识点讲授

### 1. 普通聊天和复杂任务的区别

普通聊天通常是一问一答。复杂任务则包含多个步骤、多个信息来源和多个检查点。

| 普通聊天 | 复杂任务 |
| -------- | -------- |
| 回答一个问题 | 围绕目标持续推进 |
| 主要生成文字 | 可能要调用 RAG、计算、写文件、调整计划 |
| 输出后结束 | 根据结果和反馈继续下一步 |
| 错误较容易发现 | 错误可能在流程中累积 |

复习助手如果只是解释一个概念，可以用普通提示词；如果要根据错题和讲义持续安排复习，就需要任务流程。

### 2. CoT、ToT 和 GoT：用 Prompt 引导任务过程

除了在产品里打开"思考模式"，学生还可以在 Prompt 中明确要求模型采用某种思考方式，让输出过程更细、更可检查。这里介绍 PPT 中的三种方式：CoT、ToT 和 GoT。

CoT 是 Chain of Thought，常译为"思维链"。课堂中可以把它理解为：不要让模型直接给结论，而是要求它先列条件、再分步骤分析、最后给答案。比如：

```text
请先列出已知条件和目标，再分步骤说明解题过程，最后给出结论，并检查是否遗漏每天 45 分钟的限制。
```

复习助手中，CoT 适合用在解题、错因分析、计划拆解和检查限制条件时。例如让 AI 讲一道容易出错的题，可以要求它按"已知条件 → 适用方法 → 关键步骤 → 易错点 → 答案"的顺序输出。

ToT 是 Tree of Thoughts，常译为"思维树"。它不是只沿着一条思路往下走，而是先列出几种可能方案，再比较优缺点，最后选择更合适的一种。比如：

```text
请给出 3 种复习安排方案：按知识点复习、按错题复习、按题型复习。分别比较优点、风险和适用情况，再推荐最适合我的一种。
```

ToT 适合开放任务、方案选择和复杂规划，例如比较"先补概念再刷题""先看错题再补概念""每天混合复习"三种路径。

**GoT（Graph of Thoughts，思维图）**把中间结果组织成图，节点表示信息或子问题，边表示依赖关系；不同路径的结果可以合并、复用，再共同支撑结论。PPT 用“关键因素与联系”做入门说明。例如复习助手中，“错题归类”和“讲义考点”共同决定“薄弱点”，薄弱点与“每天 45 分钟”共同约束“复习计划”，自测反馈再触发计划更新。参见 [GoT 原始论文](https://arxiv.org/abs/2308.09687)。

课堂提示示例：

```text
列出复习计划中的关键因素及依赖关系：考纲、错题、薄弱点、可用时间、自测反馈。
说明哪些步骤可以分别进行、哪些必须等待前一步结果，合并重复信息后给出安排。
```

这是一种课堂化提示练习；真正的 ToT/GoT 系统还可能有外部搜索、评估和循环控制，仅写“多想几条路线”不等于实现完整算法。

要注意，Prompt 中引导模型思考和模型原生的思考模式不是一回事：

| Prompt 引导思考 | 模型原生思考模式 |
| ---------------- | ---------------- |
| 用户在提示词里要求"分步骤""多方案比较""先自检" | 产品或模型在推理阶段投入更多内部计算 |
| 主要改变输出结构和任务流程 | 主要改变模型回答前的计算过程 |
| 学生可以看到步骤、依据和比较表 | 用户通常看不到完整内部过程 |
| 可用于普通模式，也可配合思考模式 | 是否可用取决于具体产品或模型 |

所以，更稳妥的写法不是要求模型"展示全部内心思考"，而是要求它输出可检查的依据、步骤、假设、方案比较和最终结论。CoT/ToT 能帮助模型组织回答，但不能保证事实正确；思考模式能投入更多计算，但也不能替代 RAG、搜索、代码和人工确认。

### 3. 思考模式是什么

很多 AI 产品会提供"思考模式""推理模式"或类似选项。它不是模型突然有意识，而是产品或模型在回答前投入更多推理计算，让模型进行更长的中间分析、步骤拆解、候选方案比较和自我检查，再输出最终答案。

可以直观对比：

| 普通模式 | 思考模式 |
| -------- | -------- |
| 更像看到问题后直接生成回答 | 更像先多走几步草稿、比较和检查流程 |
| 速度快、成本低 | 更慢、可能更耗额度 |
| 适合简单问答、翻译、润色、格式转换 | 适合多步推理、复杂代码、方案权衡、长链条规划 |
| 容易在复杂条件下漏步骤 | 通常更能拆解和检查 |

课堂中不要求学生看到模型完整内部思考。更合适的要求是让它输出可检查的步骤、依据、假设和结论。

### 4. 什么时候用思考模式，什么时候不用

适合打开思考模式：

- 多步数学和逻辑题；
- 复杂代码调试；
- 多方案权衡；
- 长链条规划；
- 需要严谨检查的答案；
- 容易被条件绕晕的问题；
- 需要先拆任务再执行的复习计划。

不必打开思考模式：

- 简单问答；
- 翻译润色；
- 格式转换；
- 短文本摘要；
- 低风险创意发散；
- 需要最新事实但更应该先搜索的问题；
- 已经有明确工具能直接计算或检索的问题。

局限也要清楚：思考模式更慢、更贵，不保证一定正确。如果资料缺失、提示词矛盾、问题本身有误，模型可能只是更认真地走向错误。事实核查、数学计算、代码运行和文件处理仍需要工具和人工确认。

### 5. PaE：先计划，再执行

PaE 可以简化为：

```text
Plan 计划
  ↓
Execute 执行
```

Plan 阶段要提取：

- 目标：下周三的考试；
- 背景：有两个知识点总是搞混；
- 约束：每天 45 分钟；
- 资料：老师讲义、错题记录、复习范围；
- 工具：课程 RAG、错题统计、题库、日历；
- 交付物：5 天计划、自测题、需要确认的内容。

Execute 阶段按计划生成知识卡片、调用课程 RAG、统计错题、安排日程、生成自测题、整理错因，并输出结果。

### 6. 任务拆解原则

好的任务拆解应该满足三个条件：

1. 步骤有顺序；
2. 每一步能判断是否完成；
3. 缺信息时追问或暂停，而不是编造。

复习助手可拆成：

```text
1. 提取目标和限制；
2. 确认考试范围和资料来源；
3. 调用课程 RAG 和错题记录；
4. 统计薄弱知识点；
5. 安排 5 天计划；
6. 生成自测题；
7. 根据自测反馈调整；
8. 标注需要老师确认的内容。
```

### 7. ReAct 的课堂版

ReAct 可以理解为"判断依据 -> 行动 -> 观察/评估 -> 反思调整"的循环。课堂中不要求学生展示或复述模型内部完整思考，只要求任务过程可检查。

复习助手例子：

```text
判断依据：学生有两个知识点总是搞混，需要先定位混淆点。
行动：调用课程 RAG 和错题记录。
观察/评估：错题主要集中在两个概念的适用条件被互相套用。
反思调整：计划中应先安排概念对比，再安排专项练习。
行动：生成第 1-2 天复习内容和诊断题。
观察/评估：学生诊断题第 2 题出错。
反思调整：补充两个概念的适用场景对比和易错提醒。
```

ReAct 的价值是：每一步有依据、行动和结果，出错时能追踪和调整。

对照 PPT 第 9–10 页：PaE 结构清晰、容易调试，但固定计划遇到新情况时需要重新规划；ReAct 根据执行结果调整，更灵活，但步骤更多，调试和成本控制更复杂。两者都可以用工具，也都需要完成、失败或暂停条件，不能无限循环。

PaE 的执行可以留在同一上下文中，也可以为子任务新建上下文；后者必须明确传入目标、所需资料、限制与计划，不能假设模型自动记得上一步。规划阶段也可以限定 CoT/ToT 的步骤数或方案数。

### 8. 工具调用怎样工作

工具调用不是模型自己真的打开浏览器或读取文件，而是：

```text
模型判断需要工具
  ↓
生成工具名称和参数
  ↓
外部程序执行工具
  ↓
工具返回结果
  ↓
模型基于结果继续回答
```

这里有一个容易忽略、但非常关键的分工：**模型只负责"生成调用请求"**（说出要调哪个工具、填什么参数）；**真正持有密钥、发起请求、读取文件、改动数据的是模型外面的 Agent / 程序**。所以工具的**权限、审批、校验、审计**必须由模型外部的工程来做——这不是写在提示词里就能保证的。

#### 工具说明：让模型知道何时用、怎样用

按 PPT 第 12 页，每个工具至少说明名称、用途、输入和输出。例如网页搜索接收关键词，返回网页内容；HTML 内容提取接收源码，返回正文。模型可先搜索，再提取正文，最后组织回答。工具返回的材料仍需检查来源与相关性。

#### MCP：客户端、服务器与调用链（PPT 第 13–15 页）

**MCP（Model Context Protocol，模型上下文协议）**标准化应用连接外部工具和数据源的方式。宿主应用包含客户端，客户端连接服务器；服务器提供工具信息并执行调用。模型负责提出请求，通信与执行由应用完成。协议不自动保证资料正确或操作安全，授权与参数校验仍需具体实现。参见 [MCP 架构说明](https://github.com/modelcontextprotocol/docs/blob/main/docs/concepts/architecture.mdx)。

```text
用户提出问题
  → 应用向模型提供可用工具说明
  → 模型选择工具并生成参数
  → 宿主中的 MCP 客户端发送请求
  → MCP 服务器执行工具并返回结果给客户端
  → 宿主把结果加入上下文，模型继续生成回答
```

沿用 PPT 的 `get_videos` 示例，区分三件事。以下为教学化数据结构，不是完整协议报文。

工具说明：

```json
{
  "name": "get_videos",
  "description": "获取指定主题的视频",
  "inputSchema": {
    "type": "object",
    "properties": {"topic": {"type": "string", "description": "视频主题"}},
    "required": ["topic"]
  }
}
```

工具调用参数：

```json
{"name": "get_videos", "arguments": {"topic": "AI 智能体"}}
```

示意返回数据：

```json
{"videos": [{"title": "智能体是什么", "date": "2026-09-01"}, {"title": "智能体教程", "date": "2025-12-12"}]}
```

请学生检查：工具选对了吗？必填参数齐了吗？返回内容足够回答问题吗？遇到空结果、超时或无权限时，应报告、调整或请求必要信息，不能虚构成功。

复习助手常见工具：

- 联网搜索：查最新通知、比赛报名时间、公开资料；
- RAG/课程知识库：检索老师讲义、错题解析、复习范围；
- 代码执行：统计错题分布、计算时间安排、画图；
- 表格处理：整理错题和复习进度；
- 图片/语音工具：识别手写题、图表或语音提问；
- 日历和文件工具：创建提醒、保存计划，但需要确认；
- 安全审核：检查作弊、隐私、过度承诺和高风险内容。

### 9. 反馈和安全

复杂任务越能自动做事，越需要反馈和安全边界：

- 工具结果要看来源和参数；
- 搜索要优先权威来源；
- RAG 要检查片段是否完整、是否过时；
- 代码要检查统计口径和结果；
- 写入日历、发送消息、读取敏感文件前要人工确认；
- 涉及作弊、正式评价、隐私或严重心理压力时要转人工。

## 教师答疑参考（附录，不计入 20 分钟）

1. 学生可能会问：复杂任务是不是只要打开思考模式就可以了？

   推荐回答：不是。思考模式适合多步推理和复杂规划，但如果缺少资料、需要计算、需要搜索或需要读取文件，仍然要用 RAG、搜索、代码等工具。思考模式是增强推理，不是替代工具。

2. 学生可能会问：CoT 要不要让 AI 把所有思考过程都展示出来？

   推荐回答：课堂里更建议要求它输出可检查的步骤、依据、假设、比较和结论，而不是追求"完整内心思考"。这样既方便学习和检查，也更符合实际产品对推理过程展示的限制。

3. 学生可能会问：工具调用时，如果工具返回错了，AI 会知道吗？

   推荐回答：不一定。模型通常会基于工具返回结果继续回答，所以工具参数、来源、时间和返回内容都要检查。复杂任务中要设计观察和评估步骤，必要时让 AI 标注工具结果来源并提示人工确认。

4. 学生可能会问：RAG、搜索和代码工具应该怎么选择？

   推荐回答：需要最新公开信息时用搜索；需要基于老师讲义、错题解析、校内资料时用 RAG；需要统计、计算、批量处理和画图时用代码或表格工具。选择工具要看问题需要哪类外部能力。

5. 学生可能会问：复杂任务能不能完全自动完成，不让人参与？

   推荐回答：低风险、可撤回的步骤可以自动化，例如整理资料草案、生成计划草案。读取隐私资料、保存长期记忆、写入日历、发送消息、涉及考试公平或正式评价时，必须有人确认。
